# 评测集

## 为什么

改了调度、提示词或开关之后，只能靠单元测试和实际使用才能知道变好了还是变坏了。需要一批固定的任务：每次改动后跑一遍，看成功率、耗时和花费。

## 改动

- **`evals/basic.json`**：6 个任务，覆盖换算、短诗、画头像、查资料（联网）、带测试的小程序和单页网页。每个任务写明预算、超时和期望：状态、结果里要有的字、最长耗时、最多花费。
- **`evals.py`**：通过服务自己的 API，像用户一样建任务、确认、跟到结束。一个接一个跑，免得互相影响耗时。
  - 每个任务记下：通过与否、哪里没过、排计划和执行各用了几秒、花费、尝试次数、负责人决策次数。
  - 再算一个汇总。
- **`fluidform eval [suite] --out report.json --against old.json --only 名字`**：打印每个任务和汇总，并和之前的报告比，列出变了的地方：通过的变化、耗时变化超过 25%、汇总。

## 测试

`test_evals.py`：
- 一个任务从建到结束，并判定结果；
- 结果不对或花费超了算没通过；
- 报告比较；
- 仓库里的评测集能读出来。

## 风险

- 会真的花钱：一轮大约几毛钱到一两美元，看是哪些模型。
- 任务会留在任务列表里。
- 模型的回答每次都不一样，单次的成败参考价值有限，要看几轮下来的趋势。
