# 聊天和计价做成独立的能力包

## 目标

- **聊天**从 FluidForm 本体里搬出去，成为一个能上传、能卸载的能力包。本体只做任务。
- **计价**（模型价格、费用预估、每次调用记账、会员 CLI 按套餐折算、预算上限）也搬出去，成为一个能力包。
  卸掉它，任务就不估价、不记账、不受预算限制。
- 能力包可以声明自己**需要**哪些能力：飞书机器人写明需要"聊天"，启用时没有聊天能力就提示先装上。
- 两个包随 FluidForm 一起提供，第一次启动时装好并启用（用户要的功能默认就有），也可以卸掉。

## 现成方案

- 进程模型沿用现有能力包：沙箱里的后台进程，通过 stdin/stdout 一行一个 JSON 消息。
- 消息格式用 JSON-RPC 2.0，和 MCP 一样（请求、回答、通知，双向都能发起）。这样不用自己定格式，
  FluidForm 里已有现成的读写代码（`mcp.ts`）。
- 没有找到能直接用的"给应用拆插件"的现成框架适合这里：插件要跑在沙箱里、拿不到密钥，
  常见的插件框架（同进程加载）做不到这一点。

## 新的包类型：服务（`service`）

`capability.json` 新增：

| 字段 | |
|---|---|
| `kind: "service"` | 后台进程，给 FluidForm 本体提供接口 |
| `provides: ["chat"]` | 它提供哪种能力（`chat`、`pricing`），同一种能力同时只能有一个包启用 |
| `requires: ["chat"]` | 任何包都可以写：需要哪些能力。启用时缺了就拒绝，并提示"需要先启用聊天能力"；被依赖的包不能先停用 |

- 进程跑在能力包的沙箱里：看不到用户的主目录和 FluidForm 的数据，只能写自己的数据目录，
  联网只能通过代理到它声明的域名（通常一个也不需要）。
- **它拿不到任何 API key。** 要调用模型、跑工具、读附件，都向 FluidForm 发请求，由 FluidForm 代办。
- 进程挂了自动重启，和自动化一样；连续失败就停下并在能力页显示。

## 聊天能力包（`chat`）

### 本体留下的（只做"管道"）

- 对话记录的存储（`ExecutionRun` 里 `kind: "chat"` 的记录，旧记录照样能读）、网页上的对话页面和接口路由。
- 自动化（飞书机器人）收到的消息照旧进 FluidForm，再交给聊天包。
- 本体收到消息后：存下来，交给聊天包，把聊天包的进度和回答写回记录、推给网页或飞书。
- 没有聊天包时：网页上不显示"对话"入口，`/api/chats` 等接口回 409"没有启用聊天能力"，旧对话只能看、不能接着聊。

### 搬进包里的（"怎么聊"）

- 选哪个模型、怎么换模型、换模型时的交接（`supervisor.ts` 里聊天的部分）。
- 聊天的提示词：角色、在哪里（私聊、群聊）、能用哪些工具、怎么 @ 人、`CHAT.md`。
- 记住偏好（`remembering.ts`）。
- 群里没 @ 它的话是不是在问它、上下文怎么带、只 @ 不说话怎么回（`automations.ts` 的大部分）。
- 从聊天里排任务、发文件、请平台工程师（`chat-actions.ts`）。

### 实际的接口

做的时候改成了和计价包一样的方式：由 FluidForm 在每个决定点问聊天包（上面第 3 步列的那些请求），包只做决定、
不反过来调用 FluidForm。这样模型调用、工具、记账、流式输出都留在本体原来的位置，行为和以前一样（原来的测试
和与 Python 后端的对照测试都照样通过）。下表是最初设想的"包驱动"接口，没有采用。

### 最初设想的、包向 FluidForm 发的请求（未采用）

| 请求 | FluidForm 做什么 |
|---|---|
| `models.list` | 能用来聊天的模型和它们的特点 |
| `models.converse(session, prompt, attachments, tools)` | 由 FluidForm 调模型（用 FluidForm 保管的 key，经计价包记账），进度用通知推回 |
| `tools.call(chat, tool, args)` | 在这段对话自己的文件夹里、在步骤的沙箱里跑工具 |
| `tasks.create(request, context, attachments)` | 排一个任务，等主人确认 |
| `engineer.call(chat, request)` | 请平台工程师 |
| `chat.reply / chat.progress` | 把回答、进度写回对话 |

## 计价能力包（`pricing`）

### 搬进包里的

- 每个模型的价格（目录同步里的价格字段也由它维护）、会员 CLI 按套餐折算（`cli-quota.ts`）。
- 任务和步骤的费用预估（`routing.ts` 的估算部分、`retrospect.ts` 的历史校准）。
- 每次调用记多少钱（`budget.ts`），以及预算上限：一次调用前问它"还能不能花这么多"。

### FluidForm 向包发的请求

| 请求 | 什么时候 |
|---|---|
| `pricing.estimate(plan, models)` | 排好计划后，给每一步和整个任务估价 |
| `pricing.admit(run, model, reserve)` | 每次调用模型之前：够不够预算；不够就停下，和现在一样 |
| `pricing.charge(run, call)` | 每次调用之后：按用量记账 |
| `pricing.price(model)` | 选模型时：同样够格的模型里挑便宜的 |

- 包启用但没有回答（进程挂了、超时）：**停止花钱**，任务暂停并提示，不会无限制地跑下去。
- 没有计价包时：不估价、不记账、不限预算；选模型只看评分不看价格；网页上不显示费用和预算。
  旧记录里的费用和预算照样能读、能显示。

## 分几步做

1. **框架**（完成）：`service` 类型、`provides` / `requires`、双向 JSON-RPC、生命周期、能力页显示"提供了什么、依赖什么"
   （`services.ts`，docs/design/capability-packages.md 的"服务"一节）。聊天和计价做成包之前仍由本体提供（`services.builtIn`）。
   飞书包的 `requires: ["chat"]` 放到第 4 步，和飞书包重做一起加。
2. **计价包**（完成）：`server/packages/pricing`（Node，`pricing.mjs` 是计算，`service.mjs` 是服务入口），
   随 FluidForm 提供（`bundled.ts`：第一次启动、有沙箱、允许能力包时装上并启用；卸掉后不再装回，`bundled.json` 记着）。
   本体的 `pricing.ts` 把每次估价、选模型时的费用（`pricing.costs`/`rates`）、调用前的预算（`admit`/`fits`/`allows`）、
   调用后的记账（`charge`）、会员 CLI 按套餐折算（`cli_price`，本体只读额度）、历史校准（`calibrated_each`）都发给包。
   包启用但没回答：抛 `PricingUnavailable`（属于 `BudgetExceeded`），任务照预算不够那样暂停。没有计价包：不估价
   （`plan.estimate` 为空）、不记账、不限预算、没有价格的模型也能选，选模型只看评分。
   测试里计价由包自己的代码在测试进程里回答（`tests/helpers/pricing.ts`），`tests/pricing.test.ts` 跑真的服务进程；
   和 Python 后端的对照测试（golden）结果不变。
   还没做：聊天选模型时的平局判定仍读目录价格（第 3 步随聊天搬走）；没有计价包时网页上仍显示 $0 的费用和预算输入框。
3. **聊天包**（完成）：`server/packages/chat`（`chat.mjs`、`service.mjs`），和计价包一样随 FluidForm 提供、第一次启动时启用。
   和计价一样由本体在每个决定点问包，包不反过来驱动本体（见下面"实际的接口"）。搬进包里的：选哪个模型
   （`chat.order`、飞书的 `chat.automation_model`）、提示词（`chat.opening`/`role`/`handover`，含 CHAT.md、群聊/私聊、
   工具说明、记忆说明）、回答里给 FluidForm 的行（`chat.split`、`split_sends`、`split_task`、`action_lines`）、
   行动工具（`chat.tools`、`chat.action`）、记忆（`chat.remember`/`told`/`memory`/`forget`，存在包自己的数据目录，
   旧的 `<data_dir>/memory.json` 第一次安装时搬过去）、群里没 @ 的话（`chat.hear`、`chat.judged`、`chat.frame`）。
   本体留下：对话记录、模型调用（用本体的 key、经计价包记账）、工具、发文件、排任务、飞书的状态。
   没有聊天包：不能新建或继续对话（409），`/api/start` 一律当任务，旧对话只能看，网页不显示"对话"入口。
4. **飞书包**：按官方 `lark-channel-sdk` 示例重做，写明需要聊天能力。

每一步单独测试、单独提交，旧记录都要能读。

## 测试

- 框架：一个假的服务包，双向请求、超时、崩溃重启；`requires` 缺了不能启用、被依赖的不能停用。
- 计价：装着和卸掉两种情况下，任务的估价、记账、预算上限；计价包挂了时停止花钱。
- 聊天：装着和卸掉两种情况下，网页对话和飞书消息；旧对话能读。
- 现在这些功能的测试都改成通过包来跑，结果要和现在一样。

## 风险

- **工作量大**：计价牵连 43 个源文件，聊天牵连对话、负责人、自动化几块。按上面四步做，每步都能单独验收。
- **每次调用模型都多一次进程间请求**（问预算、记账），多几毫秒，相比模型调用可以忽略。
- **卸掉计价包，任务就没有预算限制**，可能花得比预期多。能力页卸载时要明确提示这一点。
- 聊天包拿不到 key，只能通过 FluidForm 调模型，所以它能做的事受限于 FluidForm 给它的接口；
  以后聊天要新本事，可能要先在接口里加。
- 飞书机器人重复回复的问题按你的决定先不处理，到第 4 步一起重做。
