# 任务的各部分做成能力包（已批准：随附扩展）

## 目标

FluidForm 的核心只保留最基础的：用命令行（或任何界面）发起任务，选模型（会员 CLI 和 API 模型之间自动选，
或只用一种、只用指定的），执行，按固定规则重试。其余让任务做得更好的部分都是能力，可以停用、卸载、替换：

| 能力包 | 提供 | 里面是什么（现在的代码） |
|---|---|---|
| 规划（`planning`） | `planning`、`team` | 拆成多步、快速/单人任务的判断、项目简介、中途改计划、产物约定的检查；员工分派和员工之间的委托（`planner.ts`、`triage.ts` 的 quick、`briefing.ts`、`replan.ts`、`contracts.ts`、`team*.ts`） |
| 负责人（`lead`） | `lead`、`review` | 步骤失败后的决定（重试、换模型、改计划、问你、请平台工程师）、全部做完后的把关和结果总结、任务里的对话；另一个模型验收步骤结果（`supervisor.ts` 的任务部分、`leading.ts`、`review.ts`、`quality.ts` 的验收） |
| 平台工程师（`engineer`） | `diagnosis`、`engineer` | 卡住时查原因、修环境、修 FluidForm 自身、加新组件（`diagnosis.ts`、`diagnosing.ts`、`engineer.ts`、`platform-repair.ts`、`self-repair.ts`） |
| 经验（`learning`） | `learning`、`preflight`、`skills` | 任务后复盘和积累经验、开工前的环境检查、给步骤附上相关技能（`retrospect.ts`、`learning.ts`、`preflight*.ts`、`skills.ts`、`skill-discovery.ts`） |

四个包都随 FluidForm 提供、默认启用（用户要的功能默认就有）。装着时，任务的行为和现在完全一样：
现有测试和与 Python 后端的对照测试都照样通过。

## 没有这些包时，核心怎么做

| 缺少 | 核心的做法 |
|---|---|
| 规划 | 整个需求作为一步，交给一个模型做（会员 CLI 或会用工具的 API 模型，在项目里就在项目里做）。不拆步、不分员工、不改计划 |
| 负责人 | 一步失败：同一个模型再试一次，再失败换更强的模型，换过还失败就把任务标为失败。做完就结束，结果是这一步的输出。任务里不能对话 |
| 验收 | 只看步骤自带的检查命令（有的话），没有就算通过 |
| 平台工程师 | 卡住、环境缺东西时，任务暂停并写明原因，等你处理 |
| 经验 | 不复盘、不开工前检查、不附技能 |

网页上对应的部分（规划详情、员工、负责人对话、平台工程师页、复盘）在没有对应能力时不显示；命令行的 `plan` 直接排一步。

依赖：`team` 需要 `planning`；负责人的"改计划"需要 `planning`，"请平台工程师"需要 `engineer`，缺了就不提供这个选项。

## 怎么拆：随附扩展（2026-11-22 定）

最初的方案是和聊天包一样放进沙箱进程，由本体代问模型。这四块和执行器、数据库、路由缠得很深，
那样做等于重写约 1 万行，所以改为随附扩展：

- 代码放在各自的包目录 `server/packages/<id>`，本体不直接引用它们。
- 包装上并启用时，在 FluidForm 进程里加载；停用、卸载后不加载，本体按上表的方式照常做任务。
- 它们的权限和本体一样、没有沙箱，所以只接受随 FluidForm 提供的：上传或从别处安装的包不能作为随附扩展加载。
- 以后哪一块需要隔离或要让第三方替换，再单独改成沙箱服务包。

## 分几步做

1. **核心的最小任务**：没有任何任务能力包时，按上表的方式跑完一个任务（一步、固定的重试规则）；每项能力都能
   停用；网页和命令行按能力显示。
2. **规划包**：规划和员工搬出去。
3. **负责人包**：负责人和验收搬出去。
4. **平台工程师包**：诊断和平台工程师搬出去。
5. **经验包**：复盘、经验、执行前检查和技能搬出去。

每一步单独测试、单独提交，旧的任务记录都要能读、能继续。

## 进度

第 1 步进行中。已有：各决定点先问能力在不在（`features.ts`），没有规划时排成一步。还差：

- 让用户能停用（现在写死在 `provided.ts` 的 `builtIn`）；
- 没有负责人时先用同一个模型重试一次，再换更强的；
- 没有经验能力时不复盘；
- 网页和命令行按能力显示；
- 失败路径的测试。

## 风险

- **工作量很大**：涉及约 1 万行代码，是到现在最大的一次拆分，要分很多次做完。每一步结束时 FluidForm
  都是完整可用的。
- **没有隔离**：随附扩展出错或有漏洞，影响的是整个 FluidForm 进程，所以不加载第三方的。
- **平台工程师修的是 FluidForm 自己**：它做成能力以后，修复本体时的复制源码、检查、应用和
  重启留在本体，包决定怎么查、怎么改。平台工程师包坏了，用命令行停用它，本体照常工作。
- 现在的一些开关（`employee_teams`、`acceptance`、`auto_diagnose`、`preflight`、`learning_enabled` 等）先保留，
  作为能力包里的细项；以后可以再精简。
