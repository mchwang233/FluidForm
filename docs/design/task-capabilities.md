# 任务的各部分做成能力包（已批准：随附扩展）

## 目标

FluidForm 的核心只保留最基础的：用命令行（或任何界面）发起任务，选模型（会员 CLI 和 API 模型之间自动选，
或只用一种、只用指定的），执行，按固定规则重试。其余让任务做得更好的部分都是能力，可以停用、再启用（随附扩展不能卸载，也不能由第三方替换）：

| 能力包 | 提供 | 里面是什么（现在的代码） |
|---|---|---|
| 规划（`planning`） | `planning`、`team` | 拆成多步、快速/单人任务的判断、项目简介、中途改计划、产物约定的检查；员工分派和员工之间的委托（`planner.ts`、`triage.ts` 的 quick、`briefing.ts`、`replan.ts`、`contracts.ts`、`team*.ts`） |
| 负责人（`lead`） | `lead`、`review` | 步骤失败后的决定（重试、换模型、改计划、问你、请平台工程师）、全部做完后的把关和结果总结、任务里的对话；另一个模型验收步骤结果（`supervisor.ts` 的任务部分、`leading.ts`、`review.ts`、`quality.ts` 的验收） |
| 平台工程师（`engineer`） | `diagnosis`、`engineer` | 卡住时查原因、修环境、修 FluidForm 自身、加新组件（`diagnosis.ts`、`diagnosing.ts`、`engineer.ts`、`platform-repair.ts`、`self-repair.ts`） |
| 经验（`learning`） | `learning`、`preflight`、`skills` | 任务后复盘和积累经验、开工前的环境检查、给步骤附上相关技能（`retrospect.ts`、`learning.ts`、`preflight*.ts`、`skills.ts`、`skill-discovery.ts`） |

四个包都随 FluidForm 提供、默认启用（用户要的功能默认就有）。装着时，任务的行为和现在完全一样：
现有测试和与 Python 后端的对照测试都照样通过。

## 没有这些包时，核心怎么做

| 缺少 | 核心的做法 |
|---|---|
| 规划 | 整个需求作为一步，交给一个模型做（会员 CLI 或会用工具的 API 模型，在项目里就在项目里做）。不拆步、不分员工、不改计划 |
| 负责人 | 一步失败：同一个模型再试一次，再失败换更强的模型，换过还失败就把任务标为失败。做完就结束，结果是这一步的输出。任务里不能对话 |
| 验收 | 只看步骤自带的检查命令（有的话），没有就算通过 |
| 平台工程师 | 卡住、环境缺东西时，任务暂停并写明原因，等你处理 |
| 经验 | 不复盘、不开工前检查、不附技能 |

网页上对应的部分（规划详情、员工、负责人对话、平台工程师页、复盘）在没有对应能力时不显示；命令行的 `plan` 直接排一步。

依赖：`team` 需要 `planning`；负责人的"改计划"需要 `planning`，"请平台工程师"需要 `engineer`，缺了就不提供这个选项。

## 怎么拆：随附扩展（2026-11-22 定）

最初的方案是和聊天包一样放进沙箱进程，由本体代问模型。这四块和执行器、数据库、路由缠得很深，
那样做等于重写约 1 万行，所以改为随附扩展：

- 代码放在各自的包目录 `server/packages/<id>`，本体不直接引用它们。
- 包装上并启用时，在 FluidForm 进程里加载；停用、卸载后不加载，本体按上表的方式照常做任务。
- 它们的权限和本体一样、没有沙箱，所以只接受随 FluidForm 提供的：上传或从别处安装的包不能作为随附扩展加载。
- 以后哪一块需要隔离或要让第三方替换，再单独改成沙箱服务包。

## 分几步做

1. **核心的最小任务**：没有任何任务能力包时，按上表的方式跑完一个任务（一步、固定的重试规则）；每项能力都能
   停用；网页和命令行按能力显示。
2. **规划包**：规划和员工搬出去。
3. **负责人包**：负责人和验收搬出去。
4. **平台工程师包**：诊断和平台工程师搬出去。
5. **经验包**：复盘、经验、执行前检查和技能搬出去。

每一步单独测试、单独提交，旧的任务记录都要能读、能继续。

## 进度

第 1 步已完成（2026-11-22）：

- 四个随附扩展各有 `server/packages/<id>/capability.json`，能停用、再启用，不能卸载（代码随 FluidForm 一起，
  停用就是不用它）。是否提供某项能力只按随附目录里的清单算，数据目录里的记录只管开关（`extensions.ts`）。
- 上传的包不能是扩展、不能用扩展的 id，也不能声明提供这些能力。
- 没有负责人时：同一个模型再试一次，再换更强的，还失败就标为失败。
- 没有平台工程师时：做不到的步骤让任务暂停并写明原因；负责人照常做决定，但不会有诊断。
- 没有验收时：步骤自带的检查命令照跑，不通过就算这一步失败；没有命令才算通过。
- 没有经验时：不复盘，也不能手动复盘；已有的记录留着。
- 网页按能力显示。测试在 `server/tests/task-core.test.ts`。

第 2 步已完成（2026-11-22）：排计划、改计划、委派、项目简介、快速/单人判断都在
`server/packages/planning/src`，本体只通过 `planning.ts`（2026-11-28 起是端口 `ports/planning.ts`，见 capability-ports.md）在启用时动态加载。包里的代码和本体一起编译，
构建产物因此在 `server/dist/src` 和 `server/dist/packages`。留在本体的是读任务记录要用的：员工和委派的
记录怎么读（`team.ts`）、给步骤看项目文件（`briefing.ts`）、分辨对话和任务（`triage.ts`）、产物约定的检查
（`contracts.ts`，执行和验收都用）。

第 3 步已完成（2026-11-22）：验收、超时时问负责人、负责人的决定（失败后、收尾、你回答之后、提议能力）、
它的提示词和读决定的代码都在 `server/packages/lead/src`，本体通过 `lead.ts`（2026-11-28 起是端口 `ports/lead.ts`，执行决定回到本体的 `leading.ts`，见 capability-ports.md）动态加载。留在本体的是和聊天
共用的会话和对话管道（`supervisor.ts`、`leading.ts`）、改任务的动作（`leading.ts`），以及不需要负责人的检查
（步骤自带的检查命令、卡住检查，`review.ts`）。

第 4 步已完成（2026-11-22）：怎么查、怎么修环境、怎么修和扩展 FluidForm 自身（提示词和各轮流程）都在
`server/packages/engineer/src`，本体通过 `engineering.ts` 动态加载。留在本体的是按诊断结论改任务
（`diagnosing.ts`）、工作记录和预算（`engineer.ts`）、复制源码、检查、应用、提交和重启（`platform-repair.ts`、
`self-repair.ts`）。没有平台工程师时，开工前检查不通过也不再请它修，直接暂停。

第 5 步已完成（2026-11-22）：复盘怎么分析和验证、给问题起名、开工前检查、找和写技能都在
`server/packages/learning/src`，本体通过 `experience.ts` 动态加载。

留在本体的（和原表不同的地方）：

- 按记录算出的复盘和相似问题（`retrospect.ts`）、经验记录的读写（`learning.ts`）、读技能库（`skills.ts`）：
  别的能力和页面要同步读它们。是否使用仍由 `features.ts` 决定，停用时不复盘、不给技能。
- 产物约定（`contracts.ts`）、员工和委派的记录（`team.ts`）：执行时要用。
- 会话和对话的管道（`supervisor.ts`、`leading.ts`）：和聊天共用。

随附扩展用得到本体的模块（同一个进程、同一份实例）；反过来本体只经过 `ports/planning.ts`、`ports/lead.ts`、
`engineering.ts`、`experience.ts` 动态加载它们，`server/tests/extension-boundary.test.ts` 保证没有直接引用。
开关和运行中的服务（`server/tests/switching.test.ts`）：

- 停用只挡新的工作：已经开始的一次决定、检查、修复照常做完。
- 停用时，平台工程师排队和等批准的工作、没做完的复盘都留着等，再启用时接着做；重启也一样。
- 启动时先读进所有启用的扩展（启用时也马上读），所以服务运行中重建不会抽走或混用它们的代码；
  `./start.sh` 在服务运行时不再重建。
- 停用后代码不再被调用；已经加载过的要到重启才离开内存。

## 风险

- **工作量很大**：涉及约 1 万行代码，是到现在最大的一次拆分，要分很多次做完。每一步结束时 FluidForm
  都是完整可用的。
- **没有隔离**：随附扩展出错或有漏洞，影响的是整个 FluidForm 进程，所以不加载第三方的。
- **平台工程师修的是 FluidForm 自己**：它做成能力以后，修复本体时的复制源码、检查、应用和
  重启留在本体，包决定怎么查、怎么改。平台工程师包坏了，用命令行停用它，本体照常工作。
- 现在的一些开关（`employee_teams`、`acceptance`、`auto_diagnose`、`preflight`、`learning_enabled` 等）先保留，
  作为能力包里的细项；以后可以再精简。
