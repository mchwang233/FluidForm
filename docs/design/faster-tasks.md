# 小任务走得快

## 为什么

一个只有一步的任务（"画一张海边女孩的头像"），开工前要先走完全套：
- 负责人排计划：判断难度，再排计划，有时还要组队、分块，2–3 分钟；
- 执行前检查：每个任务都从头查一遍，失败了还要诊断，约 1.5 分钟；
- 验收：每一步做完，都要另请一个模型逐条审。

真正干活的时间反而没那么长。平台工程师那边也一样：它自己跑完全量测试，交回后平台又在干净沙箱里跑一遍。

## 改动

新行为都放在开关后面，默认关，这台机器上打开：

- **轻量任务**（`quick_tasks`，`triage.quick`，`api._quick_plan`）：
  - 判断：排计划前，先让最便宜的模型看一眼请求。判断为"一个模型一次就能做完、几分钟、不碰任何人的项目文件"（画一张图、写一篇短文、换算、查资料再总结），就直接生成一步的计划，跳过负责人排计划。
  - 这一步怎么定：标题、能力、要不要画图、验收标准由那个便宜模型给出，难度标为 `easy`，计划的说明写"一步就能做完"。
  - 照常排计划的情况：判断不清楚，或出错；带项目、需求变更、按用户的选择重排计划时，也不走轻量。
  - 失败了怎么办：这样的任务没有负责人，失败后走原来"没有负责人"的路：重试、诊断。终审也就没有了。
- **简单步骤不另请模型验收**（`review_easy_steps`，默认开着，即照旧验收；`review.py`）：
  - 关掉后，标为 `easy` 的步骤按它自己的结果算通过，不再另请一个模型逐条审。
  - 不受影响的：验证步骤（`verifies`），以及步骤自带的检查命令（`check`）。
- **执行前检查缓存**（`preflight_cache_minutes`，`preflight.cache_key`、`passed_before`、`PASSED`）：
  - 怎么复用：同样的工具、联网设置、是否在项目里、步骤用的模型，加上这台机器记下的环境（`sandbox.json` 改了就失效），通过一次后，在设定的时间内不再重查，直接用上次的结果。
  - 不缓存的：没通过的检查。
  - 怎么看出来：`Preflight.cached`，`run.preflight` 事件里的 `cached`。
  - 只记在内存里：重启服务就清空。
- **平台工程师和修复不重复跑全量**（`skills/platform-engineer`、`skills/platform-repair`）：
  - 干活时只跑本模块的测试；全量测试和前端构建交给平台在干净沙箱里跑，没过就把输出交回给它改。
  - 长调用的记账：CLI 已经按 0 计（`cli_free`），API 模型的工具循环每一轮都查预算，这一项不另做。

## 测试

`test_quick.py`：
- **轻量任务**：
  - 判断为轻量时，任务只有一步简单步骤，不调用负责人排计划；
  - 其他回答（不是轻量、看不懂、值不对）照常排计划；
  - 没打开开关、或带项目时，照常排计划；
  - 判断的回答按防御的方式读：能力不认识就用默认，JSON 坏了就当不是轻量。
- **简单步骤验收**：开关关掉后，简单步骤不另请模型验收，普通步骤照旧。
- **执行前检查缓存**：
  - 第二个同样的任务用上次的结果；
  - 换了设置的任务、过期之后、关掉缓存之后都重新检查；
  - 没通过的不缓存。

## 风险

- **判断错了**：把一件其实要分步的事当成轻量，就会由一个模型硬做。它失败或者做得不好时，没有负责人来改计划，只能重试、诊断，或者由用户按"需求变更"重来。所以判断的提示词把"拿不准就不算轻量"写在了前面。
- **简单步骤少了一道关**：有它自己的检查命令时还算稳；没有的话，错误要等用户自己发现。
- **缓存期间环境变了**：比如服务停了、许可证过期，在缓存期内不会被检查出来，要等步骤失败后由诊断去发现。缓存时长可以调短。

## 一个模型连续做完

### 为什么

轻量任务只管"几分钟就能做完"的事。修一个 bug、加一个功能、写一份调研报告这类中等的事，还是要走负责人排计划、拆步、交接、审查。其实这类事交给一个强模型带着工具一路做下去就够了，主流产品也都是这么做的。

### 改动

- **`solo_tasks`**（默认关）：开着时，`triage.quick` 改问 `SHAPE_PROMPT`，回答分三种：quick（同上）、solo（一个强模型带工具连续做，最长约一小时，一份结果）、plan（照常排计划）。拿不准就是 plan。
- solo 的任务只有一步，难度标 `hard`，所以调度时选分高的模型。它可以在项目里做（`needs_workspace`、`in_project`），quick 不行。
- 计划说明写"一个模型连续做完"。

### 风险

- solo 的步骤失败时没有负责人改计划，只能重试、诊断，或者由用户把它改成需求变更。

## 重启后接着做

### 为什么

服务重启时，正在跑的任务会被暂停，要等用户点"继续"。每次改代码、重启前，都得先确认没有任务在跑。

### 改动

- **`resume_after_restart`**（默认关）：启动时，被打断的任务如果不在项目里、也没有在等诊断、平台修复或平台工程师，就重新排队（`api.resumes_by_itself`），事件是 `run.restart_resumed`。
- 已完成的步骤保留结果；被打断的那一步重新跑，提示里会让模型先看看上次的工具做到了哪里（`Executor.execute` 原有的做法）。
- 在项目里的任务照旧暂停，等用户确认：它可能改了一半项目文件。

### 风险

- 被打断的那一步会重跑：画图、发请求这类工具可能会重复执行一次，钱也可能多花一次。

## 设置档位

### 为什么

开关越来越多，一个个配既麻烦又容易漏。

### 改动

- **`profile`**：`fast`、`balanced`、`careful`，每个档位打开一组设置（`config.PROFILES`）。单独写了的设置仍以单独的为准（`model_fields_set`）。默认空，所有设置保持各自的默认值。
  - `fast`：轻量任务和一个模型连续做、简单步骤不另审、检查缓存 60 分钟、重启后接着做、聊天里做小事并用工具调用。
  - `balanced`：轻量任务、检查缓存 30 分钟、重启后接着做、聊天里做小事并用工具调用。
  - `careful`：每个任务都排计划，每一步都另请模型验收。
- **在页面上选**：侧栏 **设置 → 工作方式**（`frontend/memory.tsx` 的 `ProfilePicker`，照"界面主题"那排按钮的样子做）。选了立刻生效（`Settings.use_profile`：旧档位的开关先回到默认值，再套上新的），保存在 `<data_dir>/profile.json`，启动时读回（`load_saved_profile`），比 `FLUIDFORM_PROFILE` 优先。单独设过、不跟着档位变的开关，在页面上显示有几项（`given_alone`）。

### 测试

`test_durable.py`（不在项目里的接着做；在项目里的、在等回答的、没开开关的都暂停），`test_quick.py`（solo 在项目里只排一步困难步骤；回答按防御的方式读），`test_profiles.py`（档位生效，单独设的优先，档位里只有真实存在的设置），`test_memory.py`（页面上切换档位立刻生效、换档时旧的回到默认、重启后读回），前端 `mission-actions.test.mjs`（选了档位就保存）。

## 小程序也算小事，只做要求的（2026-11-20）

### 为什么

"写一个贪吃蛇的游戏"被判断成一个强模型要长时间做的事（solo，难度困难）。那一步写了 7 个文件、约 1500 行：游戏、网页、两套测试、一个无界面演示脚本和 README，花了 8.5 分钟、$0.052。用户要的只是一个能玩的贪吃蛇。

### 改动

- **判断时**（`triage.SHAPE_PROMPT`、`QUICK_PROMPT`）：能独立运行的小程序（贪吃蛇这样的小游戏、一个脚本、一个计算器、一个网页）算 quick。solo 只留给真正费功夫的事：修 bug、加功能、由几部分组成的程序、调研报告。
- **交给那一步时**（`api.QUICK_SCOPE`、`SOLO_SCOPE`，加在没经负责人排计划的那一步说明末尾）：只做要求的，做完自己运行或检查一次，能用就交付；没要求的测试套件、演示脚本和说明文档都不用写。
- **评测集**加了"贪吃蛇"一项，要求 3 分钟内做完。

### 测试

`test_quick.py`：小游戏在提示里属于 quick；那一步的说明以"只做要求的"结尾；solo 的那一步也有这句提醒。
