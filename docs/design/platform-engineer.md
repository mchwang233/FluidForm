# 设计：平台工程师

状态：已实现
范围：`engineer.py`（新）、`self_repair.py`、`leading.py`、`supervisor.py`、`api.py`、`frontend/engineer.tsx`（新）

## 1. 为什么要加

修改 Super Partner 自身代码的能力原来只藏在任务的诊断里：某一步失败，诊断判断是平台的问题，
才会在隔离副本里改代码，检查通过后自动生效。这样有三个缺口：

1. 用户不能直接让它修一个缺陷或者加一个功能，只能先跑一个会失败的任务。
2. 负责人发现 Super Partner 缺少某种能力（一个工具、一个模型渠道、一种步骤），只能把那一步判为无法完成。
3. 平台改了什么只记在发起修复的那个任务里，看不到全部历史；生效后也不会提交到 git。

## 2. 角色

**平台工程师**专门修改 Super Partner 自身，和负责人并列，但不属于任何一个任务。

| | 负责人 | 平台工程师 |
|---|---|---|
| 管什么 | 一个任务，从规划到结束 | Super Partner 本身 |
| 改哪里 | 任务的项目目录 | Super Partner 源码的隔离副本 |
| 同一时间 | 每个任务一个 | 一次只做一件，其余排队（任务里的修复不排队，见第 4 节） |

## 3. 工单（`EngineerJob`）

每件工作是一张工单，存在 `engineer_jobs` 表里。

- 类型 `kind`：`repair`（修复缺陷）或 `component`（添加组件：模型或渠道、工具和技能、界面功能、调度和流程）。
- 来源 `origin`：`user`（用户在平台工程师页面提出）、`lead`（负责人在任务中请求）、`diagnosis`（任务的诊断判断是平台问题）。

状态：

```
组件：  queued → planning → plan_ready ──批准──→ queued → editing → validating → ready ──应用──→ applying → applied
                              │ 回复修改 → planning              │ 回复修改 → editing
修复：  queued → editing → validating → applying → applied                (检查通过就自动生效)
任一阶段：needs_input（工程师提问，回复后继续）、failed、rejected（用户放弃）、cancelled
```

- **planning**：工程师读代码，写方案（目标、改哪些文件、怎么测、需要用户决定的事），不改任何文件。
- **editing / validating**：沿用 `platform_repair.py`：在隔离副本里改，必须带测试，独立的沙箱检查
  （语法、数据库兼容、后端测试、前端测试、构建），不通过就把失败输出交回给工程师再改，最多
  `platform_repair_attempts` 次。
- **ready**：组件已通过检查，等用户看过改动后点"应用"。修复跳过这一步。
- **applying**：和原来的平台修复一样，等在途的模型调用结束，重启服务，健康检查不过就回滚。
- 应用时如果源码已经被别的改动更新过，工单回到 editing，用新的副本按已批准的方案重做。

## 4. 三个入口

1. **用户**：在任务的负责人对话里把平台工程师拉进来（见 4.1）。导航栏里没有单独的平台工程师入口；它的页面只从对话里的“在平台工程师页面查看”打开，用来看工单的完整记录。花费记在工单自己的预算上（默认
   `engineer_budget_usd`），默认用会员 CLI，不额外花钱。
2. **负责人请求组件**：新的决定 `request_component`。任务暂停（`ExecutionRun.engineer_job_id`），
   工程师先写方案，用户在任务的负责人对话里批准。工单结束（应用、失败或被放弃）
   后结果交回负责人，由它决定那一步怎么办。
3. **任务里的平台修复**：负责人决定 `repair_platform`，或者诊断判断 `STATUS: PLATFORM_REPAIR`。
   流程不变（`_fix_platform`，在任务的诊断里进行，花费记在任务上，不排队，因为任务在等它），
   只是同时记一张 `repair` 工单，在平台工程师页面上可见。生效或失败后：负责人请求的修复交回负责人
   决定（和环境修复一样），其余按原来的方式继续任务。

### 4.1 任务里的群聊

负责人面板也是一个群聊：平台工程师可以随时加入，不必等到负责人的下一次决策。起因是一次真实的经过：负责人在聊天里查清了"步骤沙箱连不到宿主机的许可证端口"，可聊天里没法采取行动，只能承诺"下次决策时再提交"，结果一直没有提交。

- **拉它进来**（`engineer_join`，工单关联到任务，**不会让任务暂停**）：
  - 用户：在面板上点"拉平台工程师进来"，选择修复或添加组件；也可以用「@平台工程师 …」直接说（`POST /api/tasks/{id}/engineer`）。
  - 负责人在聊天里：回复末尾加一行 `ENGINEER: {"kind", "request"}`（`supervisor.split_engineer`），这一行不显示给用户，换成"已请平台工程师加入"。
  - 负责人在任何一次决策里：附带 `"engineer": {"kind", "request"}`（`read_engineer`）。例如它接受了某一步的结果，同时发现平台本身有问题，这个问题也不会漏掉。
- **群里显示**：前端把负责人对话和关联到任务的工单消息（`GET /api/engineer?run_id=`）按时间合在一起显示，工单的最新一条消息下面有工单卡片：方案、提问选项、批准、应用、放弃。数据不额外复制，所以群聊和平台工程师页面总是一致。
- **@平台工程师**：有工单在等用户（方案待批准、改动待应用、提问）时，消息作为对它的回复；没有正在进行的工单时，新开一张修复工单。
- **负责人知情**：负责人收到的下一条消息前面，会附上自上次以来平台工程师工作的变化（`engineer_updates`，记录在 `ExecutionRun.engineer_seen`），所以它知道修好了没有、还在等什么。
- 负责人的指令里写明了"平台工程师"对应 `repair_platform` 和 `request_component`，用户这样说时它能对上号。

### 4.2 右下角的聊天气泡

页面右下角有一个 🛠 气泡（`engineer-bubble.tsx`），点开就是和平台工程师的聊天，不需要进任何任务。气泡上的数字是等你处理的工单数。

- 每张工单一个对话串，标明是"在这里提出"还是"来自任务「…」"。最近更新的排在最下面，工单卡片和任务群聊里的一样。
- 输入框默认回复正在等你的那一项；也可以点"改为提新需求"。新需求不用选类型：说要"添加、新增、支持……"的按组件处理（先出方案给你批准），其余按修复处理（通过检查后自动生效）（`kindOf`）。
- 导航栏里不再有"平台工程师"。完整记录页只从对话里的"在平台工程师页面查看"进入。

## 4.1 工作时看得到在做什么

工程师的一次模型调用常常要二三十分钟。只有一个"修改中"的状态，用户分不清它是在干活还是卡住了。

- **记录**：工单开始做时，执行器为它开一份只在内存里的记录（`Executor.engineer_logs[job_id]`），做完就丢掉。
  - **模型调用**：每次调用都套上 `activity.recording`，记下会员 CLI 边跑边打印的命令、改了哪些文件、说的话（目前只有 Codex 这样打印），以及 API 模型的工具调用（`tool_log`）。和步骤页用的是同一种记录。
  - **平台检查**：`PlatformRepairs.check` 通过 `on_check` 回调，记下每一项检查的开始和结果（`tool: "check"`）。
- **接口**：`GET /api/engineer/jobs/{id}/activity` 返回 `running`、`total`，以及最近的 `calls`（最多 400 条）。
- **界面**：工作页在工程师干活时多一块"正在做"。它复用步骤页的 `ToolLog` 和 `.node-activity`，每 3 秒刷新；检查项用中文名显示。不实时打印的会员 CLI 会注明"只在结束时汇报"。
- **不改变工程师的行为**：只多一份记录、多一个只读接口，所以没有另加开关。

## 5. 生效后提交到 git

工单应用成功后（新进程启动后，`_finish_platform`），由程序在当前分支上提交这次改动的文件
（`git commit -- <files>`，不带上用户已暂存的其他改动），提交信息写明工单标题和"平台工程师"。
不推送。没有 git 仓库、或提交失败时，只在工单里记一条说明，不影响生效。

## 6. 护栏

- 模型只改隔离副本，从不碰在用的源码、任务数据、凭据、git 历史和服务。
- 同一时间只有一个改动等待生效（`platform_pending`）。
- 改动必须带测试，不能删除原有测试；检查由程序独立运行。
- 组件生效前必须经用户确认；负责人请求的组件，方案也要用户批准。

## 更快生效、只用强模型、守住预算（2026-11-19）

### 为什么

看了 25 项工作的记录，有三处问题：

- **生效前等太久**：10-28 那次，从改好到生效等了 30 分钟。应用前要等所有在跑的任务把手头的步骤跑完，碰上几小时的回归就要等几小时。
- **弱模型改源码**：4 项失败里有 2 项，加上耗时最长的一项（372 分钟），用的都是 DeepSeek Flash。
- **预算没拦住**：一项预算 $2 的工作最后记了 $12.81。会员 CLI 的花费要等调用结束才记上，下一次调用前也没人检查。

### 改动

- **只等不能打断的**（`self_repair._wait_to_apply`、`cut_off_safely`）：
  - 仍然要等的：正在处理的请求、平台工程师的排查和修复、负责人的回答，以及项目里任务的步骤（打断了可能留下改到一半的项目）。
  - 其他任务的在途步骤最多等 `APPLY_WAIT_SECONDS`（5 分钟），之后重启会打断它们。重启后任务自动接着做，被打断的那一步重新跑。关掉了 `resume_after_restart` 的机器照旧全部等完。
- **只用强模型改源码**（`routing.engineers`）：
  - 会员 CLI 都可以；API 模型要能动手，并且编码分不比最强的低 5 分以上（`ENGINEER_SCORE_MARGIN`）。
  - 平台工程师的工作和任务里的平台修复（`diagnosing._diagnose_with(edit=True)`）都按这个选。
  - `cli_free` 开着时，改源码可以用会员 CLI，不受任务"不许用 CLI"的限制：这不是任务自己的工作，也不花钱。
- **每次调用前查预算**（`engineer._engineer_charged`）：
  - 预算用完就不再发起调用。工作停下来问用户（`needs_input`）："追加预算，接着做"会再加 `engineer_budget_usd`，从停下的地方接着做；"到此为止"放弃这项工作。

### 测试

- `test_platform_repair.py`：
  - 不在项目里的任务，步骤到时间就打断；
  - 项目里的任务，以及关掉自动接着做时，都等完再生效；
  - 没有这次修改时这条测试会失败（已验证）。
- `test_engineer.py`：
  - 只有强模型能改源码；没有 CLI 时用最强的 API 模型，弱的不用；
  - 预算用完后不再调用，问用户要不要追加，追加后接着做完；
  - 没有这次修改时这条测试会失败（已验证）。

### 风险

- **被打断的步骤会重跑**：花过的时间和钱白费一次。上限是 5 分钟，比起原来动辄几十分钟到几小时的等待，通常更划算。
- **单次调用仍可能超支**：一次会员 CLI 调用如果本身就很贵，在它结束前仍然拦不住，只能防住之后的调用。`cli_free` 开着时 CLI 按 0 计，不受影响。
- **只有弱模型的机器**：这时它就是最强的那个，仍会被用上。这条规则是相对最强模型的，不设绝对分数线。

## 复盘改进先记下、修环境也列在平台页、重启后接着改（2026-11-20）

### 为什么

- **复盘改进**：复盘提给平台工程师的 5 项组件里，你拒绝了 3 项，其中两项各等了你 10 小时和 5 小时。大多是只在一个任务里出现过一次的问题。
- **修环境的记录**：平台工程师修本机的记录散在各个任务里，平台页上只能看到改源码的工作。
- **重启打断**：重启打断平台工程师的工作后，它会从头再做一遍。另外有 2 项工作只写了"平台修复被取消。"，没说原因。

### 改动

- **复盘改进**（`learning._not_for_engineer`、`retrospect.runs_with`、`PLATFORM_MIN_RUNS`）：
  - 改 FluidForm 的改进，要等这个问题至少在 2 个任务里出现过才交给平台工程师。按问题的类别、键和名字统计任务数，名字把不同键下的同一原因归到一起。
  - 在这之前，改进记为"先记下"（`deferred`），写明原因。说不清对应哪个问题的，也先记下。
  - 同一个问题已经有平台工程师在处理时，也不再重复提。
- **平台页的"全部记录"多了"修环境"一组**（`engineer._environment_repairs`、`GET /api/engineer` 的 `environment`）：
  - 列出平台工程师在任务里修本机、查原因的记录：哪个任务、哪一步、谁请来的、结果。点一下打开那个任务。
  - 改源码的照旧作为工作记录列出，不重复。
- **重启后接着改**（`platform_repair.edited`、`engineer._engineer_edit`、`restore_engineer`）：
  - 副本还能用（源码没变）时，告诉模型副本里已经改了哪些文件，让它从那里接着做，不要从头来。对话里写"已经改了的保留着，接着做"。
  - 源码在这期间变了，副本就不能再用，只能重新开始。
- **说清为什么停下**（`self_repair._why_stopped`）：平台修复没说原因就停了时，写明是任务被取消或删除，还是服务重启或停止打断了它，都写明没有改动 FluidForm。

### 测试

- `test_learning.py`：只在一个任务里出现过的问题，改进先记下，不交给平台工程师；在两个任务里出现过的照旧交给它。没有这次修改时测试失败（已验证）。
- `test_engineer.py`：
  - 记录里列出修环境，不含负责人的提问、改源码的工作和还在进行的；
  - 重启后在同一个副本里接着做（没有这次修改时失败，已验证）；
  - 停下的原因。
- 前端 `mission-actions.test.mjs`：平台页列出修环境，点了打开任务。浅色、深色都截图看过。

### 风险

- **真需要的改进来得晚一点**：要等问题第二次出现，平台工程师才会处理。急的话可以直接找平台工程师。
- **修环境的列表**：每次打开平台页都要遍历所有任务。任务很多时会慢一些，最多列 50 条。
