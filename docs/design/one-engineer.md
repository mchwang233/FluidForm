# 修复都交给平台工程师

## 为什么

现在能"修"的角色有两个：诊断（修这台机器的环境）和平台工程师（改 FluidForm 的源码）。用户和负责人都要先想清楚是哪一种，才知道该找谁。

- 负责人要在 `repair_environment`、`repair_platform`、`request_component` 三个里选一个，选错了就白走一趟。
- 用户在任务页看到的是"诊断"，在平台页看到的是"平台工程师"，像是两个人。
- 负责人看不到不是它请来的诊断（用户手动点的、执行前检查开的）。这一步再失败时，它不知道已经查出了什么，可能重复修一遍，或者做出和诊断相反的决定。

## 改动

对用户和负责人来说只有一个角色：平台工程师。它被请来后先判断问题在哪，再选修法。底下的两种修法不变，权限也照旧分开：修环境的会话可以动本机、不能改源码；改源码的照旧在副本里改，测试通过后才应用。

- **负责人只说"请平台工程师"**（`supervisor.py`、`leading.py`，开关 `engineer_repairs`，默认关）：
  - 开着时，负责人的决定只剩一个 `call_engineer`，里面写 `kind`（repair 修问题，component 加组件）和证据，代替原来的三个。
  - repair 交给修复会话（现在的 `_repair`），由它判断是这台机器的问题（当场修）还是 FluidForm 的问题（`STATUS: PLATFORM_REPAIR`，转去改源码）。
  - component 照旧走 `_engineer_for_lead`，等用户批准方案。
  - 旧的三个名字仍然认得：旧记录照常显示；关着开关时行为不变。
- **修复会话以平台工程师的身份做事**（`diagnosis.py`）：提示词开头写明它是 FluidForm 的平台工程师，被请来看这一步，先判断问题在哪一边、用哪种修法，以及什么时候该转去改源码。
- **负责人看得到平台工程师在这一步上做过的事**（`supervisor.failure_message`）：
  - 失败说明里多一段"平台工程师在这一步上查过的"（`supervisor.engineer_looks`）：谁请的（负责人、用户、失败后、执行前检查）、结论、要用户做的事、报告摘要（最多 3 次）。
  - 这一条是修缺陷，不放在开关后面，附回归测试。
- **界面上叫平台工程师**（`frontend/diagnosis.tsx`、`frontend/src.tsx`、`frontend/lead.tsx`，以及后端给用户看的提示）：
  - 任务页的"诊断"卡片改叫"平台工程师"，副标题写这次是谁请的、做了什么：查原因、修环境、改源码。
  - "诊断"按钮改成"请平台工程师"，提示是"查原因并修好，在预算内继续"。
  - 时间线和负责人决定的说法也一起改（"诊断：环境已修复"改成"平台工程师：环境已修好"），加上 `call_engineer` 的说法。
  - 样式不变，只改文字。
- **说明**：使用说明里把"诊断员"一节并进"平台工程师"；`docs/ARCHITECTURE.md` 同步。

## 测试

- `test_leading.py`：
  - 开着开关时，负责人只拿到 `call_engineer`；repair 会开修复会话，结果交回负责人；component 开平台工程师的工单，任务等着。
  - 旧的三个名字仍然能解析、照旧执行。
  - 关着开关时，提示词和行为不变。
- `test_leading.py`：用户手动请平台工程师看过的一步再失败时，负责人的失败说明里有那次的结论。没有这次修改时这条测试会失败（已验证）。
- 前端 `mission-actions.test.mjs`：按钮和卡片显示新的名字；改了的文字在已有测试里一并更新。

## 风险

- 负责人以前能直接指定"改源码"，现在由修复会话来判断。如果它判断错了，在本机上修了半天才转去改源码，会多花几分钟。提示词里会写清楚什么时候该直接转去改源码。
- 只改了文字，代码里仍然叫 `diagnosis`。以后看代码的人需要知道这两者是一回事（架构图里写明）。

## 这次不做

- **平台页的记录里也列出修环境**：现在平台页只列改源码的工单（`EngineerJob`），修环境的记录在任务里（`Diagnosis`）。要合到一个列表，得把两种记录统一起来，改动大，放到下一步。
- **`auto_diagnose` 改名**：它现在同时管"失败时交给负责人"，名字容易让人误会。改名要兼容旧的 `.env`，单独做。
